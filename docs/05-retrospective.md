# 复盘

## 最难的问题

难点是划清模型判断与程序校验的边界。仅附一个文档 ID 无法证明答案有依据，但用静态规则替代全部业务判断也会拒绝正确答案。最终实现让模型根据问题、上下文和工具观测判断相关性、适用范围、冲突及下一步动作；程序负责动作协议、成功读取后的逐字完整引文、结果结构、执行预算和预期外部错误。结构检查能够验证引用确实存在，不能替代语义正确性的真实模型评估。

另一个难点是准确区分“资料不足”和“执行未完成”。没有资料、问题含糊、模型服务失败及预算耗尽各自使用不同状态，避免将故障伪装成正常拒答，或者在执行中断时给出未经核验的答案。

## 第一次设计中的错误

第一次把辅助事实索引当成答案准入条件，是设计错误。完整原文明明支持答案，只因没有同步添加 `facts` 就被拒绝；没有事实索引的两份制度即使写着 30 天和 15 天，也无法报告冲突。相同事实键的不同值还可能分别适用于总部与分公司，机械比较无法说明它们必然冲突。本轮因此移除了这类硬判定，保留原文和业务条件供模型判断。

另一个错误是把任何历史检索截断都作为持续阻塞条件。模型先做宽泛搜索，再精准检索并找到唯一相关原文，是合理的调整路径，旧规则却要求补全原来的宽泛查询。现在检索结果仍告诉模型是否截断，由模型决定扩大数量、缩小查询、补充核验或说明不足，不把旧查询变成永久障碍。

最初的 Mock 包含自然语言启发式，容易让流程测试看起来像语义能力验证。本轮改为明确选择预设场景，承认它只是测试替身。真实模型轨迹才证明工具返回如何影响后续动作，语义场景不能靠脚本分支“证明通过”。

## 保留的取舍与补充修正

使用原生 Python 循环和标准库降低评审启动成本。采用抽取式答案，让展示的业务内容对应原文；代价是表达可能比自由摘要冗长。保留逐字引用及完整句要求，防止伪造引用或删除句内限定条件；不再增加依赖业务索引的答案准入条件。

对预期服务异常仍给出明确错误和可审计记录；不再捕获所有异常，把编程错误藏成普通失败。普通 wheel 安装后的资源定位也进行了修正，避免仅在源码目录运行成功，却在安装后找不到默认知识库。

本轮新增八组反例，并在真实调用中继续发现“仅看摘要就判断具体规则缺失”的问题。这说明移除过度防御后，仍需通过提示约束和真实验收检查必要的原文核验。完整批次、失败项及修改后复测结果见 [03-evaluation.md](03-evaluation.md)，不能仅凭提示已修改就宣布修复完成。

## 本次获得的工程认识

1. 防御规则必须覆盖明确的问题，不能以保护为名改变题目允许的输入或阻止模型作出正确判断。
2. 测试既要包含错误答案被拒绝的反例，也要包含原文充分、范围明确却曾被误拒的正例。仅测试拒绝能力会奖励过度保守的实现。
3. 文档版本不自动表示优先级；相同字段的不同值也不自动表示冲突，必须结合适用范围。
4. 替换正文、删除辅助索引、增加未索引句子、缩小检索范围及从安装目录启动，比只重跑固定示例更容易暴露设计耦合。
5. 单元测试验证程序约束，显式 Mock 验证流程，真实模型运行验证语义及动态决策，三者的证据不能互相冒充。

这些是本次实现的设计观察，不等同于提交人未经记录的个人经历。

## 后续改进

优先扩充不同表达、混合条件和跨段限定语的评估集，分别衡量错误回答与错误拒答，并保留失败批次。继续检查模型是否在检索命中后读取足够原文，以及是否根据范围差异区分冲突与可适用规则。生产接入前再补充员工权限过滤、变更审计和人工升级入口，避免本题为了假设的生产需求增加不必要复杂度。

实际投入时间、执行结果及未完成项以 [03-evaluation.md](03-evaluation.md) 和提交说明为准；不把预估工时当成实测工时。用户仍要求本地交付，GitHub URL 后补，不将尚未发布的远程仓库写成已交付。
